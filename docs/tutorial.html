The Outfleek Tutorial

A guided walkthrough of a real, deployed Next.js 15 + Convex + Framer Motion e‑commerce platform built for Bangladesh — Cash on Delivery, manual bKash, a Facebook‑ad landing‑page builder, and correct Meta Pixel + Conversions API tracking. Read it side‑by‑side with the actual code.

CHAPTER 0

Getting the project running

Four commands, in order, get you from a clone to a running store.

bash
git clone https://github.com/vampxlr/outfleek.git
cd outfleek
npm install

# 1. Create your own Convex backend — writes .env.local for you
npx convex dev            # leave running, terminal 1

# 2. Seed sample products/categories, in a second terminal
npx convex run seed:run

# 3. Set an admin password (a Convex env var, never in code)
npx convex env set ADMIN_PASSWORD your-password-here

# 4. Start the Next.js dev server
npm run dev               # -> http://localhost:3000

Visit / for the store and /admin to log in with the password from step 3.

By the end of this tutorial you'll be able to: explain the app's three surfaces, read convex/schema.ts and know what an index does, trace an order end-to-end including its Meta tracking event, explain why prices are never trusted from the browser, name Framer Motion's core animation props, explain event deduplication well enough to teach it, write a unit test for a pricing rule, and make safe, deliberate changes to the codebase.

💡 Why this matters —

npx convex dev isn't background noise: it's a live connection that also pushes your backend code on every save. Without it, nothing works — not even locally.

Why Convex instead of REST + Postgres?

A traditional stack needs an ORM, a database, hand-wired websockets for the live admin dashboard, and a separate job queue (Redis + BullMQ) for retrying failed Meta calls — four moving pieces. Convex collapses all of it: reactivity is built into every useQuery, the scheduler replaces the job queue (ctx.scheduler.runAfter), file storage is built in for product photos, and there's no ORM or migrations — schema.ts is the schema.

💡 Why this matters —

For a small team shipping a COD store, every piece of infrastructure you don't have to run is one less thing that can go down at 11pm mid-order.

CHAPTER 2

Next.js App Router basics as used here

Folders under app/ become routes. [slug] is a dynamic segment — app/product/[slug]/page.tsx renders for any product slug, reading params.slug and asking Convex for that one product.

app/ (excerpt)
app/page.tsx                  ->  /            (home = product listing)
app/layout.tsx                    (wraps every page)
app/providers.tsx                 (client-side context)
app/product/[slug]/page.tsx   ->  /product/essential-black-tee
app/l/[slug]/page.tsx         ->  /l/eid-premium-black   (landing pages)
app/admin/orders/page.tsx     ->  /admin/orders
app/(policies)/privacy/page.tsx -> /privacy   (parens = not in the URL)

Server vs. client components — and why almost every page here is "use client"

By default App Router components are Server Components: rendered on the server, zero JS shipped for their own logic, no useState/browser APIs. Adding "use client" at the top opts a component (and its subtree) into the browser.

Nearly every page here starts with it, because the app is built around live Convex queries, browser state (the Zustand cart), and browser-only tracking (pixel, cookies) — none of which a server component can do.

app/providers.tsx
export function Providers({ children }: { children: ReactNode }) {
  const client = useMemo(
    () => new ConvexReactClient(process.env.NEXT_PUBLIC_CONVEX_URL as string),
    []
  );
  return (
    <ConvexProvider client={client}>
      <Tracking>{children}</Tracking>
    </ConvexProvider>
  );
}

app/layout.tsx stays a server component (sets <html>/metadata for SEO) and wraps everything in <Providers>, which creates one ConvexReactClient for the whole tree and fires a Pixel PageView on every route change.

💡 Why this matters —

"use client" is a trade-off, not a style rule: this app trades server rendering for "always-live everywhere," which is the right call for a fast-moving small catalog.

Reading the schema: why indexes exist

convex/schema.ts
products: defineTable({
  name: v.string(), slug: v.string(), price: v.number(),
  variants: v.array(variant),  // { size, color, stock } — embedded, not a join table
  active: v.boolean(),
  /* … */
}).index("by_slug", ["slug"]).index("by_active", ["active"]),

Without by_slug, looking up a product by its URL slug scans every row. by_active exists because the storefront always filters to live products only — indexing that boolean turns it into a fast index scan.

orders deliberately denormalizes: each order's items snapshot the product's name and price at purchase time, so a later price change never rewrites history on an old invoice.

orders.place — the most important function in the codebase

One mutation, seven steps: validate phone/cart → resolve landing page → loop cart items, check + decrement stock, price server-side → apply promo → compute delivery fee → insert order + mark abandoned-checkout converted → schedule the Meta Purchase event.

convex/orders.ts (excerpt)
for (const it of args.items) {
  const p = await ctx.db.get(it.productId);
  if (!p || !p.active) throw new Error("Product unavailable");
  const vi = p.variants.findIndex(x => x.size === it.size);
  if (p.variants[vi].stock < it.qty) throw new Error("Out of stock");
  const variants = [...p.variants];
  variants[vi] = { ...variants[vi], stock: variants[vi].stock - it.qty };
  await ctx.db.patch(p._id, { variants });

  const unit = landing?.priceOverride ?? p.price;  // price comes from the DB — never from the client
  subtotal += unit * it.qty;
}
// … insert order, then:
await ctx.scheduler.runAfter(0, internal.capi.sendEvent, {
  eventName: "Purchase", eventId: args.tracking?.eventId ?? no, /* … */
});

See the full function in the repo for promo and delivery-fee handling.

Why one mutation? A Convex mutation is atomic — every write inside it commits together or not at all. Two customers buying the last unit at once is handled correctly for free: whoever's mutation runs second sees the decremented stock and throws before an order is created.

Why is the CAPI call scheduled, not awaited? Mutations can't fetch() at all — only actions can reach the network — and even if they could, a slow Meta API would make the order itself hang. Scheduling means the order always writes fast, and the Meta call retries independently.

💡 Why this matters —

Things that must succeed-or-fail together go in one mutation; things allowed to fail independently and retry get scheduled out. This distinction shows up in almost every backend you'll ever build.

CHAPTER 4

State on the client

The cart lives in the browser in a Zustand store (lib/cart.ts), persisted to localStorage:

lib/cart.ts
export const useCart = create<CartState>()(
  persist(
    (set) => ({
      items: [],
      add: (item, qty = 1) => set((s) => { /* merge or push line */ }),
      // remove, setQty, clear …
    }),
    { name: "luxe_cart_v2" }
  )
);

The security lesson: never trust the client's price

Every CartItem carries a price field — but it's only ever a preview. Look at what orders.place actually accepts:

convex/orders.ts — mutation args
items: v.array(
  v.object({ productId: v.id("products"), qty: v.number(), size: v.string(), color: v.optional(v.string()) })
),
// no "price" field — the server refuses to even accept one

If someone opened devtools and submitted price: 1 for a ৳590 t-shirt, it would be silently ignored — the mutation reads p.price straight from the database, never from the client.

💡 Why this matters —

Any value that affects money, permissions, or ownership must be recomputed or re-checked on the server, every time, no exceptions. The client is a UI, not a source of truth.

CHAPTER 5

Animation with Framer Motion

1 · whileInView scroll reveals with stagger

components/store/Reveal.tsx
<motion.div
  initial={{ opacity: 0, y: 26 }}
  whileInView={{ opacity: 1, y: 0 }}
  viewport={{ once: true, amount: 0.08 }}
  transition={{ duration: 0.7, ease: "easeOut", delay }}
>
  {children}
</motion.div>

whileInView triggers the moment the element scrolls in — Framer wires the IntersectionObserver for you. once: true stops it re-animating; a parent stagger just increases delay per child (e.g. delay: i * 0.1 on a benefits list).

2 · AnimatePresence for the cart drawer

Plain React can't animate an element leaving the DOM — by the time an exit animation would run, it's already gone. AnimatePresence keeps it mounted until the exit animation finishes.

components/store/CartDrawer.tsx
<AnimatePresence>
  {drawerOpen && (
    <motion.aside
      initial={{ x: "105%" }}
      animate={{ x: 0 }}
      exit={{ x: "105%" }}
      transition={{ type: "tween", duration: 0.4 }}
    >
      {/* cart contents */}
    </motion.aside>
  )}
</AnimatePresence>

The drawer literally slides off-screen rather than vanishing — the checkout page uses the same pattern for its error banner and its bKash fields sliding open (height: 0 → "auto").

3 · Staggered word-by-word hero reveal

The homepage hero splits its headline into words, each getting delay: baseDelay + i * 0.07 — no stagger helper needed, just arithmetic on delay.

💡 Why this matters —

These three patterns cover almost every animation in the app: they're declarative React state (initial/animate/exit), the same mental model as useState.

CHAPTER 6

Payments & the Bangladeshi context

Why COD dominates: low card penetration and low trust in prepayment mean most Bangladeshi shoppers want to inspect goods before paying the courier. COD is the default payment method in checkout — any store requiring upfront payment loses most of its addressable market here.

Why there are no customer accounts: the project's own requirements are explicit — guest checkout only, because every extra step between "I want this" and "order placed" loses conversions on mobile Facebook traffic. Admin accounts exist; customer accounts don't.

Manual bKash verification: instead of integrating bKash's payment gateway, the store shows its bKash number and instructions; the customer sends money, then types back their own bKash number and transaction ID (TrxID). The order lands with payment.verified: false until an admin checks their real bKash history and flips it — cheaper and faster to ship than a gateway integration.

Delivery-zone fees and the free-delivery threshold: lib/pricing.ts's calcDeliveryFee charges an inside/outside-Dhaka fee, waived once subtotal − discount ≥ freeThreshold — all three numbers are admin-configurable, since delivery pricing changes with courier contracts.

Why abandoned-checkout capture matters for COD: "placing an order" and "paying" are separate moments — a customer who types a valid phone but never submits is highly recoverable by a phone call. Checkout debounces a save to abandonedCheckouts the moment the phone is valid, and orders.place marks it converted if they do complete.

💡 Why this matters —

Every one of these decisions traces back to how Bangladeshi shoppers actually buy. A generic Shopify-style flow built without that context would convert worse here.

CHAPTER 7

The landing-page builder

A landing page is a standalone, single-product funnel at /l/[slug]. The landingPages table doesn't store hardcoded components per page — it stores a sections array of typed content blobs:

convex/schema.ts
const landingSection = v.object({
  type: v.union(v.literal("hero"), v.literal("benefits"), v.literal("gallery"),
    v.literal("reviews"), v.literal("offer"), v.literal("sizeChart"),
    v.literal("faq"), v.literal("orderForm")),
  enabled: v.boolean(),
  content: v.any(),  // flexible per-section blob
});

components/landing/LandingPage.tsx maps each type to a matching React component (Hero, Benefits, Gallery…), reading whatever it needs from content. Building a new landing page is then admin work — pick a product, toggle sections, publish — no code, no deploy.

This is a data-driven UI: the page's shape lives in the database as data, and the frontend is a generic renderer. The alternative (one React page per campaign) would mean a deploy for every new ad test — far too slow for someone running dozens of ad variants a week.

Each landing page can also set priceOverride/deliveryFeeOverride — honored both in the display query and, critically, re-checked server-side inside orders.place itself, so the override can never be spoofed by the client. Stats (views, initiates, ordersCount) power a per-page conversion rate on the admin dashboard.

💡 Why this matters —

If a non-developer will need to create many similar variations of something frequently, model it as data and build one renderer — don't write bespoke code per instance.

CHAPTER 8

Meta Pixel + Conversions API

The Pixel is browser JavaScript that fires events like fbq('track', 'Purchase', …). Ad blockers, iOS App Tracking Transparency, and Safari's tracking prevention all quietly drop these — every lost event makes Meta's ad optimization worse.

The Conversions API (CAPI) is the server-side twin: your own backend calls Meta's Graph API directly (convex/capi.ts, a Convex action) — a server call can't be blocked by anything in the customer's browser.

The key concept: one event_id, sent to both sides

If both the browser and the server fire Purchase and Meta can't tell they're the same sale, it counts it twice. The fix is deduplication: both calls carry the exact same event_id, and Meta discards the second one it receives.

app/checkout/page.tsx
const eventId = uuid();
const res = await placeOrder({ ...,  tracking: { eventId, ...getTrackingContext() } });
// same id, fired to the browser pixel after the order succeeds:
window.fbq?.("track", "Purchase", { value: res.total, currency: "BDT" }, { eventID: eventId });

The server receives that same id as args.tracking.eventId in orders.place and passes it straight into the scheduled CAPI call.

PII hashing — on the server, never the browser

convex/capi.ts
function sha256(s) { return createHash("sha256").update(s).digest("hex"); }

const ph = sha256(normalizeBDPhone(args.customer.phone));
user_data.ph = [ph];
user_data.external_id = [ph];  // stable customer key — no email/accounts in this market

normalizeBDPhone canonicalizes any of 01XXXXXXXXX / 1XXXXXXXXX / +8801XXXXXXXXX into one form before hashing — hashing an inconsistent format would silently break Meta's matching.

fbclid → _fbc capture

When someone clicks a Facebook ad, the URL carries ?fbclid=…. The project's own requirements call this out as "the biggest EMQ lever for a COD store" — since there's no email-based matching fallback here:

lib/tracking.ts
const fbclid = params.get("fbclid");
if (fbclid && !readCookie("_fbc")) {
  const fbc = `fb.1.${Date.now()}.${fbclid}`;
  document.cookie = `_fbc=${encodeURIComponent(fbc)}; path=/; max-age=${90 * 86400}`;
}

Why Purchase is fired server-side: orders.place schedules the CAPI Purchase as part of creating the order, making the server the source of truth for whether a sale happened. The browser pixel fire is a redundant duplicate for dedup — if the tab crashes right after checkout, Meta still records the sale.

Failed CAPI calls retry up to 3 times with backoff and log every attempt to capiLogs, visible on the admin's Tracking Debug page.

💡 Why this matters —

"One shared ID across two systems so a downstream consumer can dedupe" is a general distributed-systems pattern — you'll meet it again as "idempotency keys" in payment processors and webhooks.

CHAPTER 9

Testing

A unit test calls one small piece of code directly — no browser, no server, no database — and asserts the output. tests/unit/*.test.ts runs on Vitest (npm test).

Design for testability — the real lesson here

lib/pricing.ts and lib/validation.ts are pure functions — no React, no Convex, no browser import — and they're deliberately extracted so both orders.place (backend) and the checkout page's live total preview (frontend) import the exact same math. That means the two can never silently disagree, and the money logic is 100% unit-testable without spinning up Convex or React at all.

Black box vs. white box

Black box: testing based only on documented input → output behavior, without reading the implementation. White box: reading the actual branches and deliberately exercising each one, tracked as statement coverage (% of lines run) and branch coverage (% of if/else paths taken both ways). This suite reports 98.63% statement coverage, with pricing.ts and validation.ts at 100%.

Boundary value analysis

Testing values right at, just below, and just above a threshold — off-by-one bugs live exactly there. The free-delivery threshold (৳2000) is tested at all three points:

tests/unit/pricing.test.ts
it("is free at exactly the threshold (boundary: 2000)", () => {
  expect(calcDeliveryFee({ ...base, subtotal: 2000, discount: 0, area: "dhaka" })).toBe(0);
});
it("charges a fee just below the threshold (boundary: 1999)", () => {
  expect(calcDeliveryFee({ ...base, subtotal: 1999, discount: 0, area: "dhaka" })).toBe(80);
});
it("is free just above the threshold (boundary: 2001)", () => {
  expect(calcDeliveryFee({ ...base, subtotal: 2001, discount: 0, area: "outside" })).toBe(0);
});

This proves the comparison uses >=, not > — a one-character bug these three tests would catch if someone "simplified" the operator later. A similar boundary sweep tests every valid/invalid Bangladeshi phone prefix (013–019 valid, 011/012 invalid, chosen because they're adjacent to the boundary).

A regression is a previously-fixed bug reappearing after a later change — the reason this whole suite re-runs on every future edit instead of being a one-time manual check.

💡 Why this matters —

Knowing which parts of your code are cheap to test — and designing more of your code to be like that — is the difference between a codebase you can change confidently and one everyone's afraid to touch.

CHAPTER 10

Deployment

npx convex dev connects to a personal dev deployment; npx convex deploy pushes to a separate production deployment with its own URL and env vars — a dev mistake can't leak into prod. Vercel hosts the Next.js frontend and needs NEXT_PUBLIC_CONVEX_URL pointed at the production Convex deployment.

VariableSet whereWhy
NEXT_PUBLIC_CONVEX_URL.env.local (dev) / Vercel settings (prod)Frontend needs it to open the Convex connection
ADMIN_PASSWORDnpx convex env setRead server-side only, never shipped to the browser
pixelId, capiTokenthe settings table, via /admin/settingsRuntime-configurable with no redeploy; token stripped from public reads

A real class of deploy bug: invisible characters in env vars

A classic Windows pitfall: PowerShell's default text encoding can prepend an invisible UTF-8 BOM when writing an env-var value through certain commands (Out-File, Set-Content without an explicit encoding, some pipe redirections). The value looks visually identical in your editor — but Convex's client-side URL parsing rejects it outright, with a generic error that gives no hint the real problem is an invisible leading byte.

The fix once you know to look for it: regenerate the value through a BOM-safe path (Convex's own .env.local writer is safe), or strip it programmatically.

💡 Why this matters —

"A value that looks right in every tool you check it with, but fails a strict parser" is common enough (trailing whitespace, wrong line endings, invisible Unicode) that "diff the raw bytes, not just what you can see" is a genuinely useful debugging instinct.

CHAPTER 12

Glossary

Mutation
A Convex function that writes to the database, atomically (all-or-nothing).
Query
A Convex read that automatically re-runs on the client whenever the data it read changes — "reactive."
Action
A Convex function allowed to call the outside world, but must go through a query/mutation to touch the DB.
Scheduler
Convex's mechanism to queue work for later, outside the current transaction — replaces a job queue.
Index
A precomputed lookup structure so the database can find matching rows fast instead of scanning every row.
Hydration
React "waking up" server-sent HTML by attaching listeners/state in the browser, making it interactive.
SSR / CSR
Server-Side Rendering (HTML built per request on the server) vs. Client-Side Rendering (browser builds it with JS).
Reactive query
A read whose result — and the component using it — auto-updates when the underlying data changes, no manual refetch.
Deduplication
Recognizing two tracking events represent the same real-world event via a shared ID, and counting it once.
EMQ
Event Match Quality — Meta's score for how confidently a server event matches a real ad-click/person.
COD
Cash on Delivery — the customer pays the courier in cash when the order physically arrives.
Slug
A URL-safe, human-readable identifier, e.g. essential-black-tee.
Variant
A specific purchasable configuration of a product — here, a size + color pair with its own stock.
SKU
Stock Keeping Unit — a unique id for one sellable variant; here, (productId, size, color) plays that role.
Coverage
The percentage of code your tests actually execute. High coverage doesn't guarantee correctness; low coverage guarantees blind spots.
Boundary value analysis
Deliberately testing values at, just below, and just above a threshold, where off-by-one bugs cluster.
Regression
A previously-fixed bug reappearing after a later change — why tests re-run continuously, not once.
